# Reconnecting follow-up checkpoint

The transport stayed open while successful source reads arrived up to 19,814ms apart. The UI's existing 10-second stale-source warning was accurate; its threshold was not increased.

A bounded instrumented real worker put most measured per-poll time in SQL and team projection, rather than synchronous dispatch (typically tens of milliseconds). These samples did not reproduce or fully explain the 19.8-second outlier; contention remains a possible contributor. CPU profiling located avoidable repeated task-provider membership scans for each item. A regression reproduced 256,560 provider reads with 80 native tasks and 800 tools. Index items by thread/provider and precompute native ownership once per team, preserving source order and strict-equality behavior, including NaN exclusions.

SQLite already used the thread/run index. The expensive part included extracting JSON from completed tool results every poll, although only active tool details are consumed. Keep every item row, status, ID and timestamp for counts and freshness; extract toolName/title only for running/starting/queued/pending/in_progress items. Regression checks both omitted completed metadata and retained active metadata.

These are variable-load samples, not a controlled benchmark or proof that every long gap is eliminated.

## Longer observation and status classification

A subsequent 90-second probe still observed 11 successful reads with a maximum 14,542ms gap. This disproves any claim that the two shorter probes established a complete latency fix. Another temporary instrumented run collected 60 reads: longest measured poll 3,455ms / 1,125ms CPU, and longest wait between a completed poll and its next start 3,637ms. No comparable long outlier was reproduced in that run. Windows CPU was around 99%, memory had about 5.7GiB free and zero pages-in/sec in one sample. Worker priority and power-throttling state were normal. Contention is supported by wall/CPU differences but the exact outlier cause remains unproven.

There is a separate, proven classification defect: connectionView called an open transport with stale source data Reconnecting. It now says Read delayed with warning tone and live:false, at exactly the same deadline, preserving last-read age and stale-data behavior. Real transport loss still says Reconnecting; a fresh read clears Read delayed. Tests failed with the old classification and passed with the change (23 team-model tests). This corrects the misleading reconnect report without hiding remaining source latency.
